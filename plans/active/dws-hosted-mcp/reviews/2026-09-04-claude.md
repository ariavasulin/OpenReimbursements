## Blocking findings

### B1 — AC-14 claims reverted code cannot expose trash; the plan's mechanism cannot deliver that
- **Severity:** Medium (misdirects the implementer; AC unfalsifiable as written).
- **Where:** plan.md:223 (AC-14 "reverting code cannot silently restore hard deletion or expose trash in the normal library"); plan.md:182 and Phase 4 step 2 (plan.md:342) place trash filters at the route/RPC layer; plan.md:235 (decisions row) admits "Old app ignores trash … rolling it back alone is unsafe".
- **Failure scenario:** After activation, code is reverted to the current app. The hard-deletion half holds: `photos_delete` is dropped, so old `DELETE /api/photos/:id` deletes nothing and returns 403 (`[id]/route.ts:138-143`). The trash half fails: old `GET /api/photos` selects with no `deleted_at` predicate (`api/photos/route.ts:137-147`) through `photos_select … using (true)` (`00000000000003_photos_schema.sql:47-49`), so every trashed row reappears in the library. The same policy also means any authenticated PostgREST client today can read trash rows plus `deleted_by`, `legacy_content_sha256`, and `duplicate_of` directly, outside every route the inventory recipe audits.
- **Smallest change:** Put the `deleted_at is null` predicate into the `photos_select` RLS policy for `authenticated` (new migration in Phase 1), and serve the trash view, dedupe lookup, ownership checks, and repair through the verified-session + service-role boundary the plan already prescribes for privileged reads. Both `security invoker` RPCs then exclude trash without edits, PATCH/DELETE on trash become 404 by construction, and AC-14 becomes provable in `test:db`. If the user prefers not to touch the select policy, reword AC-14 to "reverting code cannot restore hard deletion; trash exposure under reverted code is prevented only by the closed-gate/forward-fix posture" and add that limitation to the decisions row.

### B2 — The pre-merge ChatGPT/Claude connection check has no reachable non-production endpoint
- **Severity:** Medium (Verify item cannot be executed as scoped).
- **Where:** Phase 7 Verify item 3 (plan.md:414) requires connecting "the same HTTPS endpoint from an actual individual ChatGPT account and Claude account" before release; plan.md:254 sets gates closed in production and previews; plan.md:39 attaches `mcp.dws-receipts.com` to the production project; plan.md:246 forbids drills against production.
- **Failure scenario:** Both vendors connect from their own cloud (research.md:238-247), so the endpoint must be publicly reachable over HTTPS. The only named host is production. A Vercel preview deployment would need Deployment Protection bypassed, a preview-scoped shared key, an open MCP gate for that preview, and environment pointing at the isolated Supabase project. None of that is stated, so the implementer must decide it, and the photo-handoff half of the drill would otherwise touch production data.
- **Smallest change:** Name the pre-release endpoint and its configuration in Phase 7 step 3 (preview deployment URL, protection bypass, isolated-project env, gate opened for that preview only), or move the real-client check into the activation checklist (plan.md:418) explicitly and keep an SDK-client/Inspector check as the pre-merge AC-1 proof.

### B3 — "A browser integration scenario" names no runner or fixture strategy
- **Severity:** Medium (stalls a cold-start implementer on a cross-component test-infrastructure choice).
- **Where:** Phase 3 Verify item 3 (plan.md:327) "finalizes A, closes during B, reopens, reselects, and resumes only B; a second tab cannot steal a live lease"; Verify item 5 (plan.md:329) "Inspect desktop mapping/review/progress/error/cancelled states"; fixed test entry points are only `test:db` and `test:routes` (plan.md:264).
- **Failure scenario:** The repo's only runner is Vitest in a Node environment over `src/**/*.test.{ts,tsx}` (`vitest.config.ts:3-7`); there is no browser runner, and directory selection, directory-handle retention, Web-Worker hashing, and tab close/reopen cannot be exercised in jsdom. The implementer must choose between adding a browser runner with a fake directory-handle adapter at the inventory seam, or a manual drill, and the plan is silent.
- **Smallest change:** Declare the executor on the Verify line: either a third fixed entry point (`npm run test:browser`, runner named, directory-handle adapter injected at the inventory seam, lease-steal case included), or mark items 3 and 5 as recorded manual drills like the Phase 7 office drill and name the evidence artifact.

## Nonblocking improvements

- **N1 (Medium) — State the MCP transport mode.** plan.md:89 delegates envelopes to the SDK but says nothing about statelessness. Vercel functions share no memory, so the route must use a per-request/stateless transport (no in-memory `Mcp-Session-Id` sessions) and a Web-standard `Request`/`Response` handler inside the App Router route; the research already notes the current spec is stateless (research.md:230). Add one sentence to the contract and make "SDK version ships a stateless web-standard transport" a Phase 6 entry check so the implementer does not discover it mid-phase.
- **N2 (Low) — Make duplicate-object cleanup explicitly server-side.** plan.md:176-178 and Phase 2 step 2 (plan.md:284) say "remove only that attempt's unreferenced objects" without naming the owner. Authenticated users have no DELETE policy on the `photos` bucket (`20260822130200_rls_storage_scalar_subqueries.sql:68-74` covers `receipt-images` only), so the existing browser-side `deps.storage.remove` (`upload.ts:383-390`, `upload-manager.tsx:98-101`) is a silent no-op today. Name the finalize transaction (service role) as the owner and drop the browser `remove` seam.
- **N3 (Low) — Name the remedy for an ordinary uploader hitting someone else's trash.** Under plan.md:106 and plan.md:176, an employee whose bytes match a colleague's trashed row gets `restore_required` but is neither uploader nor admin, so no ordinary path resolves it. State the outcome copy ("ask an administrator, or use the MCP restore handoff") so Phase 2 and Phase 4 copy do not diverge.
- **N4 (Low) — Name how the old repair cron is suspended.** Rollout step 2 (plan.md:249) says "suspend the old repair cron/manual repair path first" but `vercel.json` crons ship with the deploy, so there is no code-level suspend before the new app lands. Name the mechanism (unset/rotate `CRON_SECRET`, which makes `repair/route.ts:394-397` return 401, or disable the cron in project settings). Note that old repair is harmless until step 3 creates the first trash rows, which relaxes the ordering.
- **N5 (Low) — Simplification candidate: three upload surfaces.** `add_photos` already routes ordinary file selection through the migration engine as a one-source batch (plan.md:153), yet the phone upload sheet keeps its own manager plus a new `photo_upload_attempts` ledger and a second claim-owner variant (plan.md:126-127). If the sheet could also be a one-source batch, one ledger and one claim owner disappear. The current choice is defensible (keep the tested phone manager) but is not in the decisions register; either record it there with its warrant or take the simplification.
- **N6 (Low, sweep-class, grouped):** (a) Phase 7 Verify (plan.md:417) uses `npx --prefix dws-app tsc …`; `--prefix` is an npm option, not an npx resolution flag, so use the same shape as the other commands (`npm --prefix dws-app exec -- tsc --noEmit`). (b) No phase is labelled scaffolding vs load-bearing; one line ("Phase 1 and the harnesses are scaffolding; Phases 2, 4, 7 are load-bearing") satisfies the critical-path gate. (c) plan.md:13 links the authoring contract by absolute out-of-worktree path; harmless for this review, brittle for later sessions. (d) Alternatives are settled upstream, but the research's signed-upload and S3-multipart options (research.md:151-165) are never named as rejected; a one-line rejection under the "Browser-led direct uploads" decision row would close the directness gate cleanly.

## Feasibility verdict

**Single PR:** feasible as a delivery unit, and the coupling argument holds: revoked direct grants, the service-side finalize transaction, trash read filters, and the global index cannot ship apart without a window where the old app either hard-deletes or double-inserts. The PR is nonetheless very large (two new test harnesses, an MCP route, two new UIs, a repair rewrite, a cutover CLI, roughly ten tables). The plan already names splitting as a reversible delivery choice; recommend landing it as per-phase commits carrying each phase's Verify evidence. The only defensible split seam is Phase 6 (MCP + issues), which is gated closed by `photo_release_state`, and it would still have to merge before activation.

**Production migration sequence:** feasible and consistent with the repository conventions (transactional additive files; concurrent index statements applied individually with the invalid-index check; write pause instead of dual-write, with a recorded reversal condition and an unmeasured outage window honestly declared). Rollback posture is sound once B1 is resolved.

**Behaviour contracts:** auth (handoff consume in one transaction, verified user before service-role use), dedupe (global claim before transfer, unique index as final arbiter), trash (fields, retention, restore rejection at expiry), repair (purge-first under one shared deadline with durable lease and live rechecks), and issue publication (digest serialization, publishing lease, marker reconciliation, `unknown` state) can each meet their stated contracts with the current code as the base.

**Weight against the requested MVP:** heavy relative to the ticket's "simplest" ask, but every heavy element traces to a decision locked in the frozen System Design (both must-ship skills, 30-day trash, global identity). The plan-added machinery (release gates, repair progress ledger, item revisions, cutover CLI with resume/rollback) is what the declared critical + live posture owes, so it is not over-assurance; N5 is the one candidate for trimming.
